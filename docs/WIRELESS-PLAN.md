## 1. 訂正 — 過去の資料の誤り（2026-08-12 修正済み）

TS52K を「Pro Micro」と書いた資料が 2 つあった。**TS52K は ATmega32U4 直載せの自作基板**で、
Pro Micro は使っていない。回路図を確認して両方直した。

| ファイル | 誤りだった記述 | 実際 |
|---|---|---|
| `qmk-archive/known-good/README.md` | 「Pro Micro (5V 16MHz)」/「Pro Micro なので `RST`–`GND` を短絡」 | 基板上のリセットスイッチ **`SW1`**（`Switch:SW_SPST` / `Button_Switch_SMD:SW_SPST_TL3342`、`RESET` ネット）。最後の手段は ISP ヘッダ **`J2`**（6ピン） |
| 〃 | 「QMK Toolbox と USB ドライバの導入には Administrator 権限が必要」 | QMK MSYS 同梱の `dfu-programmer` で通る。**どちらも不要**（2026-08-11 実機確認済み） |
| `HARDWARE-REFERENCE.md` §1 | 「ATmega32U4 / 5V 16MHz **Pro Micro**」 | ATmega32U4 直載せ。併せて基板外形 286×76mm・全部品 B.Cu・`J1` 位置も追記した |

### TS52K の基板の実態（回路図・PCB から読み取った事実）

* 外形 **約 286 × 76mm**（15u × 4u ＝ **キー領域そのもの。ベゼルなし**）。
  北端に USB コネクタ **`J1 (23.82, 43.59)`** 用の小さな出っ張りがあるだけ
* **MCU 側の部品はすべて B.Cu（裏面）**。キースイッチは F.Cu。→ JLCPCB の**片面実装**で済む
* コネクタ: `J1`(USB) / `J2`(ISP 6ピン) / `J3`(3ピン)
* リセットスイッチ `SW1`（`Button_Switch_SMD:SW_SPST_TL3342`）
* 定位板は **レーザーカットの真鍮 t=1.5mm**（「できるだけ重い金属が良い」と BOM にある）。
  ケースは FDM 3D プリント。**この真鍮板がアンテナ設計に効く**（R2-a）
* `rp2040` ブランチ `PLACEMENT.md` より: キーマトリクスの配線は
  **924 トラック / 283 ビアで引かれていて健在**。部品点数 147

## 2. 決定事項

### 2.1 ファームウェアは ZMK

QMK では無線は構造的に不可能（§12）。ZMK は MIT + Zephyr のオープンな BLE コントローラを使う。

### 2.2 MCU は Raytac MDBT50Q-1MV2 を直載せ

| 項目 | 値 |
|---|---|
| 寸法 | **15.5 × 10.5 × 2.05mm** — ATmega32U4 の QFP44 とほぼ同面積、**XIAO(3.5mm)より薄い** |
| 周辺部品 | 32MHz 発振とパスコンは内蔵。**ただし 32.768kHz(LFXO) は外付けが要る公算が大きい**（下記） |
| 電源 | **1.7–5.5V** → LiPo 直結可（LDO を省ける） |
| 技適 | **Telec (MIC) 認証あり**（FCC/IC/CE/KC/SRRC/NCC/RCM/WPC も） |
| GPIO | 48 本。**ピン数はもう制約ではない** |
| 入手 | スイッチサイエンス ¥1,287 / eleshop。大量購入は福見商事が扱う |
| PCB アンテナ版 | **MDBT50Q-P1MV2** も同等品としてある。R2-a の予備選択肢 |

> ⚠️ **32.768kHz クリスタルの訂正。** 当初「水晶内蔵で周辺部品は減る」と書いたが、これは怪しい。
> Raytac の製品ページは LFXO の内蔵有無を明記していない。一方で:
> * MDBT50Q でキーボードを作った先例（[note, 2026-05-31](https://note.com/unbangush/n/nf90252290791)）の
>   部品リストに **「クリスタル 32.768kHz 1個」が入っている**
> * [Qiita の nRF52840 カスタムボード記事](https://qiita.com/usashirou/items/87a68a8a6e0c69d738f9)も
>   「nrf52xx 系のモジュールには 32.768kHz が内蔵されていないものが多い」と書いている
>
> → **外付け前提で設計し、データシートで確認できたら省く**、という順で進める。
> 内蔵 RC 発振器で代替する設定もあるが、BLE のスリープ電流と精度が悪化するので最後の手段。

参考設計は [4pplet/cyber60](https://github.com/4pplet/cyber60)（nRF52840 直載せの 60% BLE 基板）。
**借りるのは MCU ブロック（電源・USB・SWD・アンテナ）だけ**で、マトリクスは既存資産を使う。

### 2.4 WS2812（現行 TS52K の 1 個）は載せない

**消灯していても 1 個あたり約 1mA 流れ続ける。** 電池を食い潰すので、
ZMK 界のハードウェア設計ガイド（[ebastler/zmk-designguide](https://github.com/ebastler/zmk-designguide)）は
明確に非推奨としている。「電源を切る回路を入れないなら、見た目より数か月の電池持ちを取れ」。

## 3. duplex をどうするか — 維持する

### duplex のコストは何だったか

**ダイオードの数は増えない。** 物理交点に 2 個というのは「そこに 2 個のスイッチがあり、
それぞれに 1 個ずつダイオードが付く」という意味で、**ダイオード数 = スイッチ数 = 53**。
非 duplex にしても 53 個のまま。代償は「行ネットに向きの違うダイオードが混在する」ことだけで、
得るものは**行ネット 10 本 → 5 本**。

### AVR 時代にあった唯一の危険は Zephyr/nRF で消える

旧実装で `gpio_atomic_set_pin_output_low()` を自前定義していた理由:
AVR では `gpio_set_pin_output()` → `gpio_write_pin_low()` の間に
**DDR=1 / PORT=1 で HIGH を駆動する一瞬**があり、duplex では押されたキー + ダイオード経由で
LOW 駆動中のピンと短絡しうる。これが duplex で一番いやな点だった。

**Zephyr の `gpio_pin_configure_dt(&spec, GPIO_OUTPUT_LOW)` は、
方向を出力にする前にレベルを確定させることを API として保証している。**
→ **この危険は設計として消える。**

### ZMK の既存 kscan ドライバでは duplex を表現できない

ZMK が持っているドライバ:
`zmk,kscan-gpio-matrix` / `-direct` / `-demux` / `-charlieplex` / `-composite` / `-mock` /
`-sideband-behaviors`。

`matrix` は `diode-direction` を **col2row / row2col のどちらか一方**しか取れない。
`composite`（`row-offset` / `col-offset` で複数インスタンスを合成）で 2 つ重ねる案は、
**同じ GPIO を 2 つのドライバが別々のタイミングで駆動することになり衝突する**
（既定の割り込みモードでは両者がアイドル時に逆の役割でピンを駆動しようとする）。**採らない。**

→ **out-of-tree モジュールに自作 kscan ドライバを 1 本書く。**
QMK で `CUSTOM_MATRIX = lite` にしたのと構造的に同じ判断。

### 残る本当の制約は 1 つ — アイドル時の割り込み待機

低消費電力のために「全列を LOW に駆動して行の立ち下がりを待つ」をやりたいが、
duplex では**片方の向きしか張れない**:

* 列 = 出力LOW / 行 = 入力プルアップ → **ROW2COL 側のキーだけ検出できる**
  （行プルアップ → ダイオード(アノード=行) → LOW の列。順方向）
* 同じ配置で COL2ROW 側は**逆バイアスで検出できない**

→ **アイドル中は 2 つの配置を交互に張る。** コスト見積り:

| 状態 | 交互切替の間隔 | 追加電流の概算 |
|---|---|---|
| BLE 接続中アイドル（約 100µA） | 10ms | **+25µA 程度**（誤差） |
| ディープスリープ（約 20µA） | 50–100ms | **+2〜5µA 程度** |

ディープスリープからの復帰は「最初の 1 打鍵で起きる」用途なので 100ms 間隔でも体感に出ない。

> ⚠️ この数字は**机上の見積り**。Phase B で実測して確かめること（R3-b）。

### 決め手 — 既存の配線が消える

**既存 `ts52k.kicad_pcb` にはキーマトリクスの配線が 924 トラック / 283 ビアで引かれていて健在。**
RP2040 化でも「MCU まわりだけ置き換え、マトリクス配線は原則そのまま残す」方針を取っている。

**duplex をやめると、この 924 トラックを全部引き直すことになる。**

> **結論: duplex は「ぎりぎりの技術」ではない。AVR 特有の危険は Zephyr で消え、
> 電力ペナルティは誤差、配線資産は丸ごと再利用できる。維持する。**
> ファーム側も `keyboards/ts52k/matrix.c`（165行）を移すだけで書き下ろしではない。

## 6. フェーズと関門

**関門（ゲート）= そこを通らなければ次に進まない判断点。** 金を使う順番はゲートで決める。

**RP2040 版 TS52K が進行中であることが、この計画を大きく安くする。**
ZMK は RP2040 を公式サポートしているので、**RP2040 版が完成したらそこに ZMK 版も作れる**。
そうすれば duplex ドライバ・53 キー・NICOLA を**実機・実寸・日常運用で検証できる**。
無線に残るのは nRF 固有の差分だけになる。

> ⚠️ **ZMK の RP2040 サポートは有線のみ。** RP2040 に ZMK が使える無線は無い。

| **G4** | `NICOLA-SPEC.md` の検証項目が全部通る。日常運用に耐える | Phase A を続ける |
| **G1** | ZMK が MDBT50Q で動く。USB HID と BLE。消費電流が見込みどおり | 無線を諦める。**ただし ZMK 版 TS52K（有線）は手元に残る** |
| **G5** | 検証基板でアンテナ・電源・実装が通る | 検証基板を作り直す（安い） |

**Phase A の副産物**: QMK 版と ZMK 版の TS52K が両方手に入る。無線をやめても残る資産。

**トレードオフ**: Phase A は RP2040 基板の完成待ちになる。並行して進めたければ
Phase B（¥6,300）を先に買えばよい。ただし **Phase -1 だけは今すぐ ¥1,000 でできる**ので、
順番として最初に置く価値がある。

### G3 が最重要 — 一番先に、一番安く潰す

NICOLA の設計原則1 は「press/release を物理キーに厳密対応させる」。
その帰結として**かなで「な」を押しっぱなしにすると「なあああああ」とリピートする**。
これは仕様であって、崩れると全部が崩れる。

#### ⚠️ 薙刀式は tap 方式だった — 「先例があるから安心」は成り立たない

[`eswai/zmk-naginata` の `src/naginata_func.c`](https://github.com/eswai/zmk-naginata) を読むと、
出力は**同じ関数の中で press と release を連続発行**している:

```c
raise_zmk_keycode_state_changed_from_encoded(SLASH, true,  timestamp);
raise_zmk_keycode_state_changed_from_encoded(SLASH, false, timestamp);
```

`held` に相当する記録機構は無い。**これは `NICOLA-SPEC.md` の原則1 が名指しで禁じている
`tap_code()` 相当そのもの。**

→ **薙刀式が証明しているのは「ZMK で同時打鍵の状態機械が外部モジュールとして書ける」ところまで。**
**「press/release を物理キーに厳密対応させて押しっぱなしを維持する」はまだ誰も証明していない。**

ただし見通しは悪くない:

* `raise_zmk_keycode_state_changed_from_encoded()` は `pressed` を **bool で取る**。
  ZMK 自身の `&kp` がまさに press で true / release で false を出して押しっぱなしを実現している
* eswai 氏も macOS の compose key のところでは **modifier を press したまま処理を挟んで後で release** している。
  **保持は現に可能**
* 薙刀式が tap なのは「かな入力に押しっぱなしが要らないから」であって、ZMK の制約ではない公算が高い

**結論: G3 の重要度は下がるどころか上がった。だから一番先にやる。**

#### 有線 TS52K を ZMK に移植して確かめる、はできない

**ZMK は AVR 8bit を明確にサポート対象外にしている。**
[Supported Hardware](https://zmk.dev/docs/hardware) の原文:
「ZMK doesn't support boards with AVR 8-bit processors, such as the ATmega32U4,
because Zephyr only supports 32-bit and 64-bit platforms.」

#### だが G3 に 53 キーは要らない — ¥1,000 で潰せる

確かめたいのは「`&ng` の press/release から register/unregister を出したとき、
押しっぱなしと修飾キーの組み合わせが素直に振る舞うか」だけ。
**タクトスイッチ 2 個で足りる**（1 個を文字キー、1 個を親指キーに見立てる）。
むしろ 53 キーが無いほうが切り分けやすい。

確かめること:

1. `&ng` の press で 2 キーを register して、物理キーを離すまで**押しっぱなしが維持される**か
2. 押しっぱなしで **OS のオートリピートが効く**か（「なあああああ」）
3. 修飾キーとの組み合わせ（`implicit_modifiers` / `explicit_modifiers`）が素直か
4. 同一 tick に複数イベントを raise したとき、HID レポートで**順序が保たれる**か

### 7.2 JLCPCB 基板が無駄になるリスク — ここが本丸

金額が大きいのはここだけ。

#### R2-a アンテナが飛ばない（最重要）

チップアンテナの周囲・直下に GND ベタと配線を置けない
（Raytac の指示は「No-Ground-Pad をできるだけ広く」）。
TS52K は**縁ゼロ**なので、基板の縁にアンテナを向ける定石が使えず、
**内側にキープアウトの窓を作る**か **USB の出っ張りを使う**ことになる。
さらに **F 面側に真鍮定位板 t=1.5mm** がある。MCU は B.Cu なので電波は下（樹脂底板）へ抜けるが、
真鍮板は反射・離調の要因になる。

> **検知が遅いのが一番の問題。基板を作ってからでは遅い。**
> → **Phase C の検証基板でキープアウト形状と真鍮板を再現し、通信距離を実測する。**
> 予備の選択肢として **MDBT50Q-P1MV2**（PCB アンテナ版）も残しておく。

参考: nRF52840 の実測レンジ報告は、内蔵アンテナで 15〜20m、外部アンテナで 70m 程度。
キーボードの使用距離（〜2m）には大きな余裕があるので、**多少劣化しても実用には届くはず**。
ただし真鍮板の影響は実測しないと分からない。

#### R2-d MDBT50Q をどう実装するか — 手はんだ以外の道が 2 つある

懸念は「技適の関係でモジュールは国内で買う必要があり、JLCPCB に実装を頼めないのでは。
そこだけ空いた基板を手はんだするのは厳しいのでは」というもの。**前例を当たった結果、その心配は要らない。**

**道1: JLCPCB の支給部品（consignment）** — 第一候補。
**自分で買った部品を送って実装してもらう正規のサービス**がある
（[How to consign parts](https://jlcpcb.com/help/article/how-to-consign-parts-to-jlcpcb)、
[Consignment Part Terms](https://jlcpcb.com/help/article/consignment-part-terms-conditions)）。
スイッチサイエンスで技適付きの正規品を買って送れば **手はんだはゼロ**。条件:

* JLC の部品番号が要る。無ければ申請してエンジニアの承認を得る
* ばら部品も受け付けるが**追加のハンドリング費用**がかかる
* **予備を余分に送る**必要がある（実装ロス分・最低数量）
* 支給部品の品質は JLCPCB の責任外

**道2: MDBT50Q だけ後付けで自宅リフロー** — 先例がある。
[MDBT50Q でキーボードを作ろう（note, 2026-05-31）](https://note.com/unbangush/n/nf90252290791) は
**MDBT50Q + ZMK** というまさに同じ構成で、**100×100mm のリフロープレート + はんだペースト + ステンシル**で
自分で実装している。しかもこの人は**「リフローが必須」**としたうえで、
**「はんだ付けが死ぬほど苦手な人はむしろリフローのほうが良いのでは」**と書いている。
つまり **前例の世界では「手はんだ vs 諦める」ではなく「自宅リフロー」が標準解**。
ステンシルは JLCPCB が基板と一緒に作ってくれる。リフロープレートは数千円。

> ⚠️ この人の失敗談: ステンシルの寸法を指定しなかったら**巨大なステンシルが届いて管理に困った**。
> 発注時に寸法を指定すること。

**TS52K には道1 が向いている。** 部品点数 147・286×76mm で、既に JLCPCB PCBA を使っている。
全部を自宅リフローするのは非現実的。道2 は**検証基板（Phase C）で使う**とちょうどよく、
本番前のリハーサルになる。

**技適について補足**: 技適（工事設計認証）は Raytac がモジュールの**型式**に対して取っているもので、
購入経路に紐づくものではない。ただし正規品・マーキング付きであることの担保は国内代理店経由が確実。
**そもそも JLCPCB が MDBT50Q を在庫している可能性は低い**ので、どのみち支給部品か後付けになる。

> ⚠️ 一般論として、**底面のみにパッドがあるモジュールは手はんだできない**（Moko MK08a / Ebyte 等）。
> MDBT50Q はキャステレーション主体なので後付けが効く。**フットプリントを起こす前に
> データシートで底面パッドの有無を確認すること。**

#### R2-e MCU が物理的に入らない

スペースバー手前は高さがぎりぎり。配置候補は本人検討中（RPG 周り / 右端 ESC の下など）。判断材料:

* MDBT50Q は **高さ 2.05mm**。XIAO(3.5mm) や ATmega32U4 + 水晶より薄い。**有利**
* **RPG 周りは避けたい** — ロータリーエンコーダは金属筐体で、アンテナ近傍に置きたくない
* **右端 ESC の下は基板の角に近く、キープアウトを取りやすい**
* USB は既存 `J1 (23.82, 43.59)` を流用できる
* 部品は全部 B.Cu（JLCPCB の片面実装を維持）

#### R2-g 既存マトリクス配線の流用が効かない

既存の 924 トラックは **ATmega32U4 のピン位置に向かって収束している**。
MDBT50Q は位置もピン順も違うので、そのままでは繋がらない。

ただしこれは `rp2040` ブランチで既に一度やった作業と同じ。`PLACEMENT.md` は
「古い ATmega の配線が残した末端（スタブ）の並び順に合わせて GPIO を割り当てた結果、
スタブの順序とパッドの順序が完全に一致し、**マトリクス同士の交差はゼロ**」と記録している。
**同じ手順を MDBT50Q でやり直す。** 先に MDBT50Q のピン配置を見て、
既存スタブの並び順に合う GPIO 割り当てを決めること。

> **nRF52840 固有の注意**: マトリクスの入力ピンは **Port 0（P0.x）か Port 1（P1.x）の
> どちらか一方に揃える**と消費電力が下がる。GPIO 割り当てのときに考慮する。

### 7.3 その他

**R3-c NICOLA が再現できない** — 影響はプロジェクトの目的そのもの。
**先例（薙刀式）は tap 方式なので、これは先例にならない**（§6 G3）。だから G3 を最初に置く。
なお eswai 氏の実装が示しているのは「QMK のロジックがほぼそのまま C として使える」ことで、
本人も「基本のかな入力は数時間で動いた」と書いている。移植の骨格としては有効。

**R3-d ZMK の破壊的変更** — 起きる前提。§11 参照。

**分割機のタイミング問題は該当しない** — ZMK で親指シフトをやるときの唯一の本質的リスクは、
分割キーボードで peripheral 側のタイムスタンプが「central の**受信時刻**」になることによる
同時打鍵判定の破綻（`app/src/split/central.c` が `k_uptime_get()` を入れている）。
BLE 接続間隔 7.5ms 分の非対称な揺らぎが乗り、前後関係が逆転することさえある。
**TS52K は一体型なのでこの問題が丸ごと存在しない。** 移植先として条件が良い。

```
  config/ts52k.keymap

sadaoikebe/zmk-ts52k     ← Zephyr module
  zephyr/module.yml
  boards/                board 定義（MDBT50Q 直載せなので shield ではない）
    arm/ts52k_rp2040/    Phase A 用（RP2040 版 TS52K）
    arm/ts52k/           Phase B/D 用（MDBT50Q）
  drivers/kscan/         duplex kscan ドライバ
  dts/bindings/
  src/                   NICOLA 状態機械
```

### Phase -1 — G3 を潰す（¥1,000、今すぐ）

1. XIAO RP2040（or 手持ちの RP2040 ボード）にタクトスイッチ 2 個を配線
2. `zmk-config` / `zmk-ts52k` を作り、GitHub Actions でビルドが通ることを確認。
   **`west.yml` で ZMK を SHA 固定**
3. 最小の `&ng` behavior を書く。`zmk,kscan-gpio-direct` で 2 キー
4. UF2 をドラッグ&ドロップ（BOOTSEL）
5. **§6 の確認項目 4 つを通す** → **G3**

**Zephyr / devicetree / モジュール構成の学習がここに集中する。** ここが一番の学習コスト。

### Phase A — RP2040 版 TS52K に ZMK 版を作る（¥0）

**RP2040 基板の完成が前提。**

**A-1 duplex kscan ドライバ**

`drivers/kscan/kscan_duplex_matrix.c` + `dts/bindings/kscan/sadao,kscan-gpio-matrix-duplex.yaml`

```
row-gpios                  5本（物理）
col-gpios                  6本
rows = <10>  columns = <6> 論理
debounce-press-ms / debounce-release-ms
debounce-scan-period-ms    押鍵中のスキャン間隔
idle-alternate-period-ms   アイドル時に2つの配置を切り替える間隔
```

中身は `keyboards/ts52k/matrix.c` の 2 パススキャンそのまま:

| QMK | Zephyr |
|---|---|
| `gpio_atomic_set_pin_output_low(p)` | `gpio_pin_configure_dt(&p, GPIO_OUTPUT_LOW)`（自前の atomic ヘルパは不要） |
| `gpio_atomic_set_pin_input_high(p)` | `gpio_pin_configure_dt(&p, GPIO_INPUT \| GPIO_PULL_UP)` |
| `gpio_read_pin(p)` | `gpio_pin_get_dt(&p)` |
| `read_cols_on_row()` / `read_rows_on_col()` | そのまま（論理行 `NUM_ROW_PINS + row` の扱いも同じ） |
| `debounce()`（quantum） | **ZMK の `drivers/kscan/debounce.c` を流用** |
| 変化を返す | ZMK の kscan コールバック `callback(dev, row, col, pressed)` |

**段階を分ける**: (1) ポーリング（10ms 固定）→ (2) 押鍵中は 1ms → (3) アイドル交互割り込み。
(3) は Phase B（nRF）で電流を測りながら詰めてもよい。

**A-2 53 キーの定義**

`ts52k_rp2040.dts` に 10×6 の matrix transform と 53 キーの物理レイアウト、EC11 エンコーダ。
`keyboard.json` から機械変換できる。
**NICOLA なしの素 QWERTY キーマップ**を用意する
（`ts52k_default.hex` と同じ「マトリクスか状態機械かの切り分け基準」を ZMK 側にも持つ）。

**実機で 53 キー全部・ロールオーバー・duplex のゴースト無し・エンコーダ両方向** → **G2**

**A-3 NICOLA 移植**

* **`eswai/zmk-naginata` を構造の雛形にする。** ZMK を fork せず、`&kp` の代わりに `&ng` を
  全キーに割り当てる方式。`behavior_naginata.c` 755 行 + `naginata_func.c` 797 行。
  **ただし出力方式（tap）は真似しない。押しっぱなしを維持する**
* ZMK 本体の `app/src/behaviors/behavior_hold_tap.c` を併読する。
  `captured_events[]` に保留 → `k_work_delayable` のタイムアウトで判定 → `ZMK_EVENT_RAISE_AT()` で再発行、
  という構造が **NICOLA の追い越し防止バッファとタイムアウト判定と同じ形**
* `nicola_table.c`（247行）はほぼそのまま移る
* フラッシュ/RAM は問題にならない（薙刀式で 25% / 18.5%）。**AVR の 28,672 バイト天井から解放される**

| QMK | ZMK / Zephyr |
|---|---|
| `process_record_user()` | `on_binding_pressed` / `on_binding_released` |
| `record->event.time` | `event.timestamp` |
| `register_code16()` / `unregister_code16()` | `raise_zmk_keycode_state_changed_from_encoded(kc, true/false, ts)` |
| modifier 付きキーコード | encoded keycode に含まれる（`implicit_modifiers` / `explicit_modifiers`） |
| `defer_exec()` / `extend_...` / `cancel_...` | `k_work_schedule` / `k_work_reschedule` / `k_work_cancel_delayable` |
| `timer_read()` | `k_uptime_get_32()` |
| `layer_on()` / `layer_off()` | `zmk_keymap_layer_activate()` / `_deactivate()` |
| 別の behavior を呼ぶ | `zmk_behavior_invoke_binding()` |
| タイミング付き出力列 | `zmk_behavior_queue_add()`（マクロが使っているもの） |
| `KC_INT4/INT5/LNG1/LNG2` | `INT_HENKAN` / `INT_MUHENKAN` / `LANG1` / `LANG2` |
| `rules.mk` / `config.h` | `CMakeLists.txt` + `Kconfig` + `zephyr/module.yml` + `dts/bindings/*.yaml` |

`&ng` を割り当てないキー（`&kp LCTRL` 等）は behavior が呼ばれない。保留のフラッシュが要るなら
`ZMK_LISTENER` + `ZMK_SUBSCRIPTION(zmk_keycode_state_changed)` で補う。
**外部モジュールのリスナはリンク順で ZMK 本体より先に呼ばれる**ので
`ZMK_EV_EVENT_CAPTURED` で握りつぶし、あとから `ZMK_EVENT_RAISE()` で出し直せる。

> ⚠️ ZMK のドキュメントの警告: 「外部モジュールは ZMK 側で定義されたイベントを
> capture/handle したまま解放しないでいてはいけない」。
> `CAPTURED` を返したら必ず `ZMK_EVENT_RELEASE()` か `ZMK_EVENT_RAISE_AT()` で始末する。
>
> ⚠️ devicetree のノード名は、locality が `BEHAVIOR_LOCALITY_CENTRAL` でない場合
> **8 文字以内**という制約がある。

**検証は `NICOLA-SPEC.md` の項目をそのまま使う** → **G4**:
単独打鍵 / 同時打鍵 / 押しっぱなしリピート / ロールオーバー / 追い越し / 小指シフト併用 /
英数の数字・記号 / モディファイア / タイムアウト。**日常運用に入れて確かめる。**

### Phase B — nRF 固有の差分（¥6,300）

Phase A を通していれば、ここで残るのは nRF 固有のことだけ。

1. `boards/arm/ts52k/` を書く（クロック、USB、フラッシュパーティション、GPIO）。
   参考: Adafruit_nRF52_Bootloader の **Raytac MDBT50Q-RX 用定義**、**cyber60**
2. 評価ボードに SWD で直焼き（`west flash` / `nrfjprog` / `pyocd`）
3. **USB HID → BLE ペアリング → `&out OUT_TOG` で USB/BLE 両方で同じ挙動**を確認
4. duplex ドライバのアイドル交互割り込みを実装し、**消費電流を実測**（§3 の見積りと突き合わせ）
5. LiPo で動かし、電池持ちを外挿 → **G1**

**UF2 ブートローダは Phase D に回してよい。**
Adafruit_nRF52_Bootloader の MDBT50Q-RX 用定義をコピーして LED / ボタンのピンだけ変える。
初回だけ SWD で焼けば以後はドラッグ&ドロップ。
（Adafruit ブートローダの既定では **P0.18 を GND に落とすとブートローダに入る**。
本番基板ではここをタクトかブリッジ可能なパッドに出す。）

### Phase C — 検証基板（本番基板を守るための保険）

**目的: 本番基板を起こす前に、基板固有のリスクをまとめて潰す。**

100×100mm 以内の小基板に、本番と同じものを載せる:

* MDBT50Q-1MV2 + **本番と同じアンテナのキープアウト形状と GND ベタ**
* 電源（LiPo 直結 or LDO、充電 IC、スライドスイッチ）
* USB コネクタ、TC2030、32.768kHz クリスタル
* 2×2 または 3×3 の duplex マトリクス

確かめること:

1. **真鍮定位板を載せた状態での通信距離**（一番大事）
2. LiPo での実消費電流と、実際の電池持ちの外挿
3. MDBT50Q のフットプリントと実装が通るか（**自宅リフローのリハーサルにもなる**）
4. duplex が実基板で安定するか

→ **G5**。**数千円で、数万円の本番基板を守れる。**

### Phase D — 本番基板

* cyber60 の MCU ブロックを土台に、TS52K の外形・キー配置へ。マトリクス配線は既存を流用（R2-g）
* MDBT50Q-1MV2 / 32.768kHz / LiPo / 充電 IC / スライドスイッチ / TC2030 / 既存 `J1`
* 技適を維持するため **モジュールは改造せず載せるだけ**。アンテナ直下は GND/配線をあけておく
* UF2 ブートローダをここで入れる
* **真鍮定位板を付けた状態で通信距離と電池持ちを実測**

## 10. 基板設計の材料（Phase C / D 用）

出典は主に [ebastler/zmk-designguide](https://github.com/ebastler/zmk-designguide)（ZMK 界の
ハードウェア設計ガイド。公式ではないがコミュニティで検証されている）と、実際の作例。

### 電源・充電

| 選択肢 | 特徴 |
|---|---|
| **TP4056** | 単純。抵抗 1 本で充電電流を決める（5kΩ → 250mA）。充電中に MCU へ給電するためショットキー 1 本 |
| **BQ24075** | USB 電流を動的に制限（典型 500mA）。不足分を電池から補える。LED を積むなら有利。ISET 3.9kΩ → 約 230mA。SYSOFF で未接続時に電池を切れる |

* **保護つきパウチセルを使えば保護回路は不要。** 保護なしの円筒セルを使うなら
  DW01A（過放電・過充電カットオフ）+ FS8205（デュアル MOSFET）が要る
* 電源スイッチは**どのモジュールにも載っていない**。自分でスライドスイッチを電池の + 側に入れる
* **極性を間違えると発火する。** splitkb も明示的に警告している
* 電池残量: 分圧抵抗（ZMK の事実上の標準値がある）は LiPo の非線形な放電曲線で精度が悪い。
  **MAX17048 フューエルゲージ**を積むと精度が上がる

### 電池

* 定番は 3.7V LiPo パウチ。**301230（110mAh、3×12×30mm）** / **401230** / 400〜900mAh
* コネクタは **JST PH 2.0mm**。多くの人は B+/B− に直接はんだ付けしている
* 日本では、小型 LiPo は **400Wh/L 未満なら電気用品安全法（PSE）の対象外**

### 電池持ちの実測報告（他人の作例）

| 構成 | 実績 |
|---|---|
| ディープスリープ | 約 **20µA**（基板全体） |
| BLE 接続中アイドル | 約 **100µA 以下** |
| 一体型・非分割 | **約 1 か月**（通常使用） |
| 110mAh 301230・分割の central | 5〜7 日（8時間/日） |
| [roBa](https://booth.pm/ja/items/6010869)（360mAh + トラックボール） | **約 3 週間**（8時間/日） |
| 分割・ドングルなし | 2〜4 週間 |
| 分割・ドングルあり | 5〜8 か月（central をドングルに逃がすため） |

**TS52K は一体型・トラックボールなし・LED なしなので、条件はいいほうに入る。**

### USB 保護

* コネクタ: HRO Type-C-31-M-12（トップマウント）/ M-14（ミッドマウント）が定番
* CC ピンのプルダウン抵抗でクライアントとして認識させる
* フェライトビーズ（高周波ノイズ）+ TVS アレイ（過電圧・逆電圧）+ ヒューズ

### レベルシフタ

**通常は不要。** WS2812C_2020 は 2.7V のロジックレベルを許容するので 3.3V 直結でよい。
（そもそも今回は WS2812 を載せない。§2.4）

### モジュール実装の一般則

* **底面のみにパッドがあるモジュールは手はんだできない**（Moko MK08a / Ebyte 等）。
  MDBT50Q はキャステレーション主体
* Holyiot 18010 のように**外部 LDO が要る**モジュールもある（XC6206P330）
* HV モード（VDDH に電池直結、内部 DC-DC）に対応したモジュールなら効率が上がる。
  MDBT50Q の 1.7–5.5V はこれに該当する可能性が高い（**要確認**）

### nRF52840 固有

* **マトリクスの入力は Port 0（P0.x）か Port 1（P1.x）のどちらか一方に揃える**と消費電力が下がる
* **P0.18** が Adafruit ブートローダのリセット/ブートローダ進入ピン
* WS2812 のデータ線や I2C の SCL/SDA は「低周波 I/O」に分類されるピンを避ける

## 11. ZMK について分かったこと

### バージョン運用

* 最新のタグ付きリリースは **v0.3.0（2025-08-01）**で**1 年前**。実質全員が `main` で運用している
* ZMK 公式が [Pin your ZMK version（2025-06-20）](https://zmk.dev/blog/2025/06/20/pinned-zmk) を出して
  「バージョンをピンせよ」と告知している。**`west.yml` で SHA 固定する**
* Zephyr 4.1 が `main` にマージ済み（2025-12-09 告知）。次期 **v0.4 の破壊的変更は HWMv2**
  （Hardware Model V2）。**out-of-tree の board が対象**で shield は影響を受けない。
  → **今回は board を書くので当たる。** 1 回の移行作業として見込んでおく

### サポート対象

* **nRF52840 / 52833 / 5340** — 無線の本命
* **RP2040 / RP2350** — サポートされるが**有線のみ**（ZMK が使える無線が無い）
* STM32（F401/F411 等）、Microchip SAMD21 — 有線
* **AVR 8bit（ATmega32U4）は明確に対象外**（Zephyr が 32/64bit しか対象にしない）
* ESP32 は実質不可（Zephyr の USB OTG が不完全）。nRF54L15 はまだ ZMK 対応なし

公式 board 定義がある RP2040 機:
**Adafruit KB2040 / SparkFun Pro Micro RP2040 / Seeed XIAO RP2040 / Boardsource Blok / QT Py RP2040**

### 出力

* **USB と BLE を同時に扱える。** `&out OUT_USB` / `OUT_BLE` / `OUT_TOG`。選択はフラッシュに保存される
* **自動フォールバックあり**: USB 出力中に切断されたら最後の BT プロファイルに戻る（逆も同様）
* → **無線版でも、そのまま普通の有線キーボードとして使える**
* **ネイティブの 2.4GHz 独自無線モードは無い**（Nordic の独自プロトコルは
  nRF Connect SDK のライセンスが厳しいため）。「ZMK ドングル」も中身は BLE で、
  ドングルは central の役割を電池から逃がすためのもの
* BLE の実測レイテンシは 5〜10ms 程度（接続間隔 7.5ms）

### 拡張のしかた

* **モジュール（Zephyr module）が公式に推奨される拡張手段。**
  「可能な限りモジュールで足せ」とドキュメントに書いてある。**ZMK 本体の fork は不要**
* behavior は devicetree バインディング（`compatible` / `#binding-cells`）+ C ドライバ
  （`behavior_driver_api` / `BEHAVIOR_DT_INST_DEFINE`）で定義する
* イベントは `ZMK_LISTENER` / `ZMK_SUBSCRIPTION`。戻り値は
  `ZMK_EV_EVENT_BUBBLE`（次へ）/ `HANDLED`（止める）/ `CAPTURED`（止めて所有権を取る）
* **優先度はリンク順で決まり、外部モジュールが最優先**（ZMK 本体より先に見る）

### ZMK Studio

* GA 済み。USB/BLE 経由でキーマップを再フラッシュなしに編集できる
* **「新しい behavior を定義する」ことはできない**（❌ と明記されている）。
  できるのは**既存の behavior をキーに割り当てる**ことだけ
* → **NICOLA の実装そのものは Studio では作れない。** 今回の計画には直接関係しない

### 参考になる既存モジュール

* [eswai/zmk-naginata](https://github.com/eswai/zmk-naginata) — 薙刀式。構造の雛形（**出力方式は真似しない**）
* [urob/zmk-leader-key](https://github.com/urob/zmk-leader-key) — `ZMK_LISTENER` でキーを握りつぶす実例
* [urob/zmk-adaptive-key](https://github.com/urob/zmk-adaptive-key) — explicit modifier の正しい扱い
* [kot149/zmk-layout-shift](https://github.com/kot149/zmk-layout-shift) — US→JIS 変換。日本人作者
* [ssbb/zmk-listeners](https://github.com/ssbb/zmk-listeners) — devicetree で宣言的にリスナを書く
* [mctechnology17/awesome-zmk](https://github.com/mctechnology17/awesome-zmk) — 一覧

### 日本語圏の状況（2025〜2026）

* 「**作業用には ZMK、競技用には QMK**」という使い分けが定着（QMK は 1ms 未満のレイテンシ）
* nice!nano が国内で買えないため、**XIAO nRF52840 が事実上の標準**になっている
* **親指シフト/NICOLA の日本語圏は今も圧倒的に QMK。** ZMK 側の先行者は薙刀式勢
* eswai 氏は**既製のコントローラボード**（BLE Micro Pro 等）を使っていて、
  モジュールを自分で基板に載せてはいない。
  → **ファームの前例は eswai 氏、モジュール実装の前例は note の記事**、と分けて参照する

## 12. 補足 — なぜ QMK では無理か

upstream QMK の無線は `bluefruit_le` / `rn42` の **AVR 専用 2 ドライバだけ**で、2022 年から動いていない。
`BLUETOOTH_DRIVER` に指定できるのは `bluefruit_le` / `rn42` / `custom` の 3 つ。
Bluetooth 系キーコード 15 個のうち **9 個が今も "not yet implemented"**。

新しく足す動きも止まっている:

* コアメンテナ tzarc の無線リワーク PR #24365 — 2024-09 に draft、**2025-04 以降動きなし**
* コミュニティの BT マルチプロファイル PR #26199 —
  **メンテナのコメントゼロのまま stale bot に 2026-07-26 に自動クローズ**
* 未マージの Docs PR #25837 が公式見解を書いている:
  「**QMK の無線サポートは不完全であり、無線コードがリファクタされるまで
  新しい無線キーボードは追加しない**」

抽象化層（`quantum/connection/`、`host_driver_t` へのバインド、接続キーコード）は
2024-08〜2025-05 に入ったが、**その下にドライバが無い**。

**根本原因はライセンス。** Nordic SoftDevice はクローズドバイナリで GPL-2.0+ の QMK に同梱できない。
QMK 自身が [Proprietary Vendor Libraries](https://docs.qmk.fm/proprietary_libs) で
「ベンダの Bluetooth スタックを GPL ファームウェアに含める法的に安全な方法はない」と明言している。
CH582 の QMK ポートも「WCH の無線ライブラリがリポジトリに入っておらず、
公開ソースだけでは BLE ファームがビルドできない」状態。
**ZMK が MIT + Zephyr のオープンな BLE コントローラを使うのは、この回避のため。**

QMK 最大の無線ベンダだった **Keychron も 2026 年の新無線ライン（Q Ultra、8000Hz / 660時間）を
ZMK に切り替えた。**

**BLE Micro Pro を採らない理由**: nRF52840 で本物の QMK `keymap.c` が書ける唯一の選択肢で、
日本語圏の実績も厚い（遊舎工房で購入可、BOOTH のぎけす屋 ¥5,000）。しかし:

* **ファームウェアのソースが 2020-08 で凍結**（`sekigon-gonnoc/qmk_firmware` の `nrf52` ブランチ）。
  最後のリリースは 2023-11。ベースは QMK 0.9/0.10 世代
* **今回捨てた 2022-01 のフォークよりさらに古く、`defer_exec()` も無い可能性が高い**
* 直近のコミットはユーザのキーマップ JSON 追加であって、ファームウェア本体の開発ではない

**6 年前の QMK に戻ることになり、今回の移行の意味が消える。** 却下。

**検討して落としたもの**:

* **KMK**（CircuitPython）— README に「**もはや積極的にメンテナンスされておらず、限定的な延命状態**」と明記。
  Python の実行時間も同時打鍵判定に不利。eswai 氏もメモリ制約を問題として挙げている
* **ESP32** — ZMK 非対応。Zephyr の USB OTG が不完全で、キーボード用 MCU として不適という結論
* **nRF54L15** — 技適はあるが ZMK 対応がまだ無い。2027 年に再検討
* **RMK**（Rust/Embassy）— nRF52840 BLE 対応で活発。実績と日本語圏の情報が薄いので今回は見送り
* **自前で Zephyr から作る** — マトリクススキャン・デバウンス・分割・電源管理・ブートローダ・
  設定保存・BLE プロファイル管理を全部作り直すことになる。**ZMK モジュールを書くほうが厳密に楽**
